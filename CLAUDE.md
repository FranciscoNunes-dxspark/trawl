# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Trawl is a keyboard-driven SQL Server client for the terminal, built with Ink (React for the terminal) on Node 22+. It is Tiller's sibling (`C:\Team\Tiller`, a git client): the shared pieces (`text.js`, `ui/parts.jsx`, `ui/hooks.js`, `mouse.js`, `selection.js`, `clipboard.js`, `jsx-hooks.js`, `register.js`, `version.js`, `help-layout.js`, `ui/HelpView.jsx`, `keymap.js`, `usercommands.js`, `palette.js`, `ui/Palette.jsx`, `run.js`, `credentials.js`, `claude-cli.js`, `family.js`, `scripts/build.js` and itself; `run.js`, `credentials.js` and `claude-cli.js` are in the apps that use them, so one missing here isn't drift) differ from Splice's (Tiller's successor, which has the same script), ignoring the apps' names, and exits with 1 on drift; `--diff` shows the lines. Keep them the same: a change to one goes into Splice too, and anything only one app needs lives in its own file (Splice keeps its diff colouring and PR list out of `parts.jsx` and `hooks.js` that way). Plain JavaScript ES modules with `.jsx` for components; no TypeScript, no linter config. The README is the user-facing spec; when behaviour changes, update it too.

## Commands

```bash
npm test                                                       # whole suite (node:test)
node --import ./src/register.js --test test/sql.test.js        # one file
node --import ./src/register.js --test --test-name-pattern="WHERE" test/*.test.js   # tests matching a name
npm run demo                                                   # run against the in-memory demo (needs a real TTY)
node bin/trawl.js query.sql --connect club-a                  # open a script on a saved connection
npm run build                                                  # Bun-compiled executable for this machine → dist/
node scripts/logo.js                                           # regenerate assets/ from src/glim.js
node scripts/shared-check.js ../splice [--diff]                # drift in the files shared with a sibling app
```

`patches/ink+6.8.0.patch` (applied by `patch-package` on `npm install`, so CI and the release builds get it too) keeps Ink's width and tokenize caches from one frame to the next rather than starting each frame empty, which about halves the cost of a keystroke. Upgrading Ink means checking `build/output.js` still has `OutputCaches` and remaking the patch (`npx patch-package ink`), or dropping it once Ink does this itself.

`--import ./src/register.js` is required whenever Node loads `.jsx`: it installs a module hook (`src/jsx-hooks.js`) that compiles `.jsx` with esbuild on import. There is no dev build step. CI runs `npm test` on Linux and Windows, so path handling and line endings must work on both (`.gitattributes` forces LF).

Releases are automatic, as in Tiller: every push to main (except Markdown-only ones) runs the Release workflow, which publishes the latest release's version with the patch raised, or `package.json`'s version when that's higher (bump it there for minor or major). It sets the version in the runner before building and commits nothing back, so `package.json` on main lags behind the releases. Compiled builds get the version via `process.env.TRAWL_VERSION` (defined by `scripts/build.js`), which also sets `COMPILED` (and defines `NODE_ENV` as production, for React's faster build); from a checkout `src/version.js` reads `package.json`, and the update check is skipped.

## Architecture

The layering, bottom to top:

- **`src/sql.js`**: pure T-SQL text handling, where most tests point. `mask()` blanks comments, strings and quoted names while keeping offsets, and everything else works on the mask: `splitBatches` (GO), `splitStatements` (the Query view's units), `classify`/`classifyScript` (is it a write, and which statements are dangerous), value formatting, CSV/JSON.
- **`src/db.js`**: the only place queries reach a server, through tedious, with its adapters for the other kinds of connection: `src/db-postgres.js` (pg) and `src/db-mysql.js` (mysql2), loaded on first use, each a session with the same interface (they run a script a statement at a time, split by `dialects.js`, and track the transaction from the protocol or the statements). A connection's `kind` (`postgres`, `mysql`, else SQL Server) picks one, and **`src/dialects.js`** (pure) holds what differs: quoting, TOP or LIMIT, how a transaction begins, the catalog, plan and activity queries (each shaped like SQL Server's, so `buildSchema` and `buildActivity` read them all), and statement splitting. Use `dialectOf(session or conn)` rather than writing T-SQL into anything that runs on every kind. A session is one connection, like an SSMS tab, so transactions and temp tables carry over between runs. `runScript` splits on GO and collects `{ sets, messages, stopped, ms }`; errors are `DbError` with the server's number, the line in the whole script, and `partial` results. Hitting the row limit cancels the request on purpose (`stopped`). A dropped connection is a `DbError` with `lost` (`connectionLost` reads each driver's errors; `notRun` when the session was found closed before anything was sent), and a session that ends by itself goes through `ended(session)`; `App`'s `query` reconnects (`reopen`) and reruns only what `actions.js` `afterLostConnection` says is safe. A connection with `ssh` goes through `src/ssh.js`, which starts the system `ssh -N -L` (keys or an agent only: `BatchMode`) and stops it with the session.
- **`src/demo.js`**: an in-memory session with the same interface, used by `--demo` and the tests. Anything new a session must do needs both drivers.
- **`src/connections.js`**: `/add` parsing, tedious options, and `connectionRows` (the Connections list grouped by `folder`, as DataGrip does). **config.json never holds a secret**: Azure SQL tokens come from `az` (`src/azure.js`, which calls az's Python directly on Windows, as Tiller does, and also adds a server's firewall rule after error 40615 or `/firewall`, through App's `az` and `publicIp` props, which tests stub), and SQL login passwords live in the OS credential store. Sonar hands Azure SQL over as a `/azure-sql <server> …` line you paste (`actions.js` `azureSql` finds or adds the connection; `trawl --azure-sql`, parsed in `src/launch.js`, does the same). A connection's `passwordFrom` ({ subscription, resourceGroup, app, slot }) has `db.js` read a login's password from that App Service's connection strings through az when the store has none or its one is turned down (`signIn`); a session that signed in that way carries `freshPassword`, which App saves and removes.
- **`src/credentials.js`**: that store, reached through tools the OS already has, never a native module (the Bun build must keep working): PowerShell P/Invoking Credential Manager on Windows, `security` on macOS, `secret-tool` on Linux. Secrets cross on stdin/stdout, not argv (except macOS's `security`). Lookups take over a second on Windows, so they're cached per process. `db.connect` finds a password as: the one passed in, the connection's `passwordEnv` variable, the store; a missing one, or a stored or typed one the server turns down, is a `DbError` with `needsPassword`, and `App`'s `connect` then asks (`ctx.askSecret`, a masked field in the confirm slot) and saves it only once it has signed in. Tests use `memoryCredentials()` and App's `open`/`credentials` props.
- **`src/schema.js`**: `SCHEMA_SQL` reads the catalog in one batch; `buildSchema` shapes it into `{ database, databases, objects, foreignKeys }` for the Explorer, completion and `/describe`. A new result set there needs the demo's `schemaSets` to answer it too.
- **`src/actions.js`**: every user-facing operation, written once; keys and slash commands call these with `ctx`. The safety rules live in `runSql`: read-only refusal, the danger confirmation, and wrapping writes in `BEGIN TRANSACTION` when the connection commits manually (`commitMode`: `conn.commit`, else manual for production, as DataGrip's Tx: Auto/Manual; `/tx` changes it).
- **`src/edit.js`**: editing results in place, pure. `editTarget(sql, sets, schema, { kind })` decides whether a result is the rows of one table with its primary key (reading the mask: one SELECT, one table in FROM, which select-list items are plain columns) and returns `{ table, keys, columns, kind }` or `{ reason }`; `App.query` stores it on the results as `edit`. Its `TYPES` table says, per kind, how typed text becomes a literal (`toLiteral`, `valueLiteral`) and which types are exact enough to match on. Changes are staged in App (`ctx.changes`: `"row:col"` → text or null, and rows to delete) and `saveScript` turns them into a script where every statement must hit exactly one row whose changed columns still hold what was read, written per kind: SQL Server one TRY/CATCH batch inside a savepoint; Postgres one `DO` block checking `ROW_COUNT`; MySQL statements each under a `-- trawl:one row: <message>` line that `db-mysql.js` checks against `affectedRows` (FOUND_ROWS, so an UPDATE counts the rows it found). On those two the script depends on `transaction` (one will be open when it runs: `saveEdits` works it out as runSql's wrapping does), which puts it in a savepoint, and `saveRecovery` is what `runScript`'s `recover` runs when it fails (back to the savepoint, or MySQL's ROLLBACK). `saveEdits` runs it through `runSql` with `keep` (the grid stays) and `recover`. The demo recognises the batch by its `-- trawl:edit` marker and only counts rows. Typing into a cell is focus `'cell'`, handled like the console's `'editor'`.
- **`src/commands.js`**: the slash-command table and completion, same shape as Tiller's.
- **`src/ui/App.jsx`**: layout, focus, the prompt, overlays, the activity log, the open script's file watcher, and **`ctx`**. `ctx.query` runs SQL visibly (spinner, esc cancels, history, transaction count afterwards); read the `Object.assign(ctx, {...})` block before adding an action. Live values are getters in the object created once above it (`session`, `schema`, `console`, …): `Object.assign` would copy a getter's value, not the getter. It names the terminal window through the `setTitle` prop, which `cli.jsx` writes as an OSC sequence (and restores on exit); tests pass a recorder or nothing.
- **The console** (`src/editor.js`, `src/ui/ConsoleView.jsx`): the Query tab's SQL editor. Editing is pure functions over `{ lines, row, col }`; the component only maps keys to them. Typing is its own focus, `'editor'`: App's dispatcher ignores every key then, and `ctx.setEditing(false)` waits a microtask so the esc that stops typing isn't also a global key. Key handlers must edit `ctx.console` (the latest text), never the render's `editor` prop, or fast typing loses keys. App's `setConsole` records every change to the text in an undo history (`ed.record`/`undo`/`redo`, `{ past, future }`); typing passes `merge` so a word is one step, and undo itself passes `record: false`. Its text is saved to `console.sql` beside the config. Suggestions while typing come from `src/complete.js` (pure): `completeAt(editor, schema)` reads the mask around the cursor (the word, a `x.` qualifier, the keyword before it) and `tablesIn` the statement's FROM/JOIN aliases (`joinConditions` turns foreign keys into ON conditions); `signatureAt` gives the syntax line for the call the cursor is in (`SIGNATURES` for built-ins, `params` from the schema for procedures and functions); the view only keeps `{ index, force, moved }` and works the list out again from `ctx.console` on every key, and draws it over the text rows below the cursor.
- **`src/ui/*View.jsx`**: one component per tab. Views must check `ctx.viewHasKeys()` at the start of their `useInput` handlers so keys don't fire while the prompt, an overlay or a confirm has focus. `useListNav` in `src/ui/hooks.js` is the shared cursor/scroll logic.

Claude (`src/ai.js`, `src/mcp.js`): a connection's `ai` level (`off` / `schema` / `results`, default `schema`) decides what Claude may see, and both the MCP server and `/ask` check it. `trawl mcp` is a hand-rolled JSON-RPC server over stdio (no SDK): stdout carries only protocol messages, so log to stderr. It reads config fresh per call, queues requests per connection (Claude calls tools in parallel; a session runs one request at a time), refuses anything `classifyScript` flags as a write, and wraps reads in a transaction it rolls back. It logs to `claude-history.jsonl`, never config.json, because it runs beside the app as a separate process.

DataGrip import (`src/datagrip.js`): brings each data source's DataGrip folder (`group`) across as `folder`, and files existing folderless connections on re-import (`plan.file`). It reads `DataGripProjects/*/.idea/dataSources(.local).xml`, `JetBrains/DataGrip*/options`, and `JetBrains/DataGrip*/dataSourcesHistory/*/data_sources_history.xml` (where recent DataGrip versions keep most data sources), newest version first, one entry per uuid. It parses with regexes, not an XML library: the files are machine-written and flat. Never touch `c.kdbx` / `c.pwd` (DataGrip's encrypted passwords); SQL logins are asked for their password on first connect instead. Imported names keep off the demo connections' names, which `--demo` would otherwise hide and then drop on save.

Updates (`src/update.js`): the only network call besides the database. Once a day `App` asks for the latest release and, in the downloaded build, installs a newer one in the background, as Tiller does (`installUpdate`: download next to the executable, check `SHA256SUMS.txt`, swap by renaming; on Windows the running exe is renamed aside and `removeOldExecutables` deletes it on a later start). `"autoUpdate": false` only announces it. Release file names must match `TARGETS` in `scripts/build.js`. `App` receives `checkLatest` and `installUpdate` from `cli.jsx`, only in compiled builds; tests pass fakes (or nothing, which turns checks off), so the suite never reaches GitHub or replaces anything.

Glim (`src/glim.js`, `src/ui/Glim.jsx`): the anglerfish mascot's pixel art and mood-from-session logic, as Tiller's Knot. `assets/` is generated from it by `scripts/logo.js`; don't hand-edit those files. The accent is blue (`theme.accent`, also Glim's outline).

Mouse (`src/mouse.js`, `src/selection.js`; copied from Splice, whose `docs/mouse.md` has the design shared with Keel): `terminalMouse` strips SGR mouse reports out of `stdin.read` before Ink sees them and hands them to `App` as the `mouse` prop (`{ subscribe, enable, stdout, claimDrags }`); tests pass a fake (`test/clicks.test.js`). Asking for the mouse stops the terminal selecting text, so Trawl does it: Ink draws through `mouse.stdout`, which keeps the last frame; a drag is painted over it in reverse video (again after every frame) and copied on release through `clipboard.js` (`src/selection.js` is the pure part). Clicks reach `App` on release, and only when the button didn't move. On Windows the console only sends the mouse as text in VT input mode: Node 22.17+ sets it with raw mode, the Bun builds set it through `bun:ffi`, older Node gets no mouse. `App` hit-tests the tabs, prompt and suggestions itself and gives the main area's events (`y` relative to it, `double` on a double-click) to the component on screen, which registers with `useMouse(ctx, handler, { top })` from `hooks.js` (`top`: where it starts in the main area, as the results under the console do). Views name their `useInput` handler `keys` so a double-click can call `keys('', { return: true })`, except where `↵` runs a statement (History, a file's statements): there a click only picks. `useListNav` has `pick(row)` and `scrollBy(n)`; the wheel leaves the cursor where it was until a key moves it (the console and the Results columns do the same with their own `free` refs). A view's rows start one line under its panel's top border, plus any header lines it draws above them (Results: the column names and the line under them); the console maps a click to a column with `editor.js`'s `clickAt`. The console also selects with the mouse itself: `useMouse`'s `drags(press)` says where it does, `App` passes that to `mouse.claimDrags`, and a drag starting there skips the screen selection and arrives move by move (`{ drag, x, y, from }`, the last with `release`) as an editor selection, copied with `ctx.copySelection`. Clicks count up to `triple`. The claim, `top` and `drags` are in Splice too, which uses none of them yet.

The Explorer is the server as a tree: `schema.databases` (system databases last), the current one opened up to its objects; `↵` on another is `/use`, which reconnects. `useListNav`'s `start` puts the cursor on the first object rather than on a database above it.

Clipboard (`src/clipboard.js`): through the OS's own tools, as `credentials.js` (PowerShell's `Set-Clipboard`, `pbcopy`, `wl-copy`/`xclip`/`xsel`), falling back to OSC 52 over SSH or when they fail. `App` takes it as the `clipboard` prop; tests pass a recorder.

Your own commands and keys, and the palette (shared with Splice: `src/usercommands.js`, `src/keymap.js`, `src/palette.js`, `src/ui/Palette.jsx`, all pure but the last): `userCommands(config.commands, builtins)` and `parseKeymap(config.keys, views)` are worked out in `App` (`custom`, kept while those two don't change), and what they leave out is said once at start-up. Your commands are command objects with `user: true` whose `run` is `ctx.runUserCommand`: `expandLines` fills in `$1`/`$*`, and each line goes through `runLine` (what `submit` runs), which resolves false when the line threw, logged an error (`errorCount`, counted in `addEntry`/`updateEntry`) or had a question answered no (`declines`, in `onConfirm`), so a list stops there. `findCommand(name, user)` and `suggestionsFor`'s `lists.user` take them, and the `?` window's sections are `custom.sections`. Keys are rewritten where they come in, not in each view: `useKeyTranslation` (`hooks.js`) wraps Ink's input emitter, so a mapped key reaches every `useInput` handler (views and App's dispatcher alike) as the key it stands for, or is swallowed and its command line run; it applies only while focus is `'view'` with no overlay or confirm, and it is also where `ctrl+p` opens the palette (from a view or the prompt, never while typing in the console or a cell). A key picked in the palette is sent the same way (`sendKey`, untranslated) from an effect once the view is back on screen; a command that takes arguments is prefilled instead.

Theme and text: `src/theme.js` has a dark and a light palette (`DARK`, `LIGHT`); `applyTheme(config)` copies one into `theme` (the Theme setting, `auto` reading `COLORFGBG`) and the accent over it (a preset accent takes its `light` shade), at start-up in `cli.jsx` and from Settings. Every colour comes from `theme` and is read while drawing: a module-level table of colours uses getters (`KIND` in `ExplorerView.jsx`) or a function (`COLORS()` in `ConsoleView.jsx`), never values copied at import, which would keep the palette Trawl started with. Use `BULLET` instead of `⏺` (Windows draws it wide), and `src/text.js` (`fit`, `fitSegments`, `stringWidth`) for width-aware truncation, never `.length`.

## Tests

`test/app.test.js` is end-to-end: it renders `<App>` against the demo connections with `ink-testing-library`, types keys into stdin and asserts on `lastFrame()`. Use its `until(check, what)` helper to wait for frames rather than fixed sleeps. Other test files are plain unit tests of the pure modules. Nothing in the suite needs a real SQL Server.

## Keeping things in sync

Adding or changing a key or command touches several places: the handler (view or `App.jsx`), `src/commands.js` for slash commands, the `?` window's sections in `src/help.js` (data: `[keys, what they do]` rows, drawn by the shared `src/help-layout.js` and `src/ui/HelpView.jsx`; the slash commands section comes from `commands.js` by itself), and the tables in `README.md`. Commit messages are short sentences describing the change, without type prefixes.
